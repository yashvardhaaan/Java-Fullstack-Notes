# 07 — Data-Flow Analysis — GATE CSE Notes

## 🎯 GATE Priority: ⭐⭐⭐⭐⭐ VERY HIGH

**Data-Flow Analysis** is the foundation for many compiler optimizations.

It is directly connected to:

* Reaching Definitions
* Available Expressions
* Live Variables
* Constant Propagation
* Copy Propagation
* Common Subexpression Elimination
* Dead-Code Elimination
* Register Allocation

For GATE, this is one of the **highest-value Compiler Design topics**.

---

# 1. What is Data-Flow Analysis?

Data-flow analysis determines how information about a program's variables or expressions **flows through the Control Flow Graph (CFG)**.

Example:

```text
B1:
    x = 10
       ↓
B2:
    y = x + 5
```

Information:

```text
x = 10
   ↓
B2
   ↓
x is known to be 10
```

The compiler uses this information to optimize the program.

---

# 2. Why Do We Need Data-Flow Analysis?

Consider:

```text
x = 10
y = x + 5
z = y * 2
```

The compiler can determine:

```text
x = 10
y = 15
z = 30
```

This can enable:

* constant propagation
* constant folding
* dead-code elimination

---

# 3. Control Flow Graph ⭐⭐⭐⭐⭐

Data-flow analysis is generally performed over a **Control Flow Graph (CFG)**.

### CFG

* Node → Basic block
* Edge → Possible control flow

Example:

```text
        B1
       /  \
      B2  B3
       \  /
        B4
```

Meaning:

```text
B1 → B2
B1 → B3
B2 → B4
B3 → B4
```

---

# 4. Basic Block

A **basic block** is a maximal sequence of consecutive statements having:

* one entry point
* one exit point

Example:

```text
B1:
    a = b + c
    d = a * 2
    e = d + 1
```

There is no jump into the middle of the block.

---

# 5. Data-Flow Information

Data-flow analysis associates information with program points or basic blocks.

Usually we calculate:

```text
IN[B]
OUT[B]
```

where:

* `IN[B]` = information entering block B
* `OUT[B]` = information leaving block B

---

# 6. Transfer Function ⭐⭐⭐⭐⭐

A block transforms incoming information into outgoing information.

General form:

```text
OUT[B] = F_B(IN[B])
```

where `F_B` is the **transfer function** for block `B`.

Conceptually:

```text
       IN[B]
          ↓
   ┌─────────────┐
   │ Basic Block │
   └─────────────┘
          ↓
       OUT[B]
```

---

# 7. Meet Operator ⭐⭐⭐⭐⭐

If a block has multiple predecessors, we need to combine their information.

This combination is called the **meet operation**.

Example:

```text
       B1
      /  \
     B2  B3
      \  /
       B4
```

At `B4`, information comes from both `B2` and `B3`.

We need:

```text
IN[B4] = MEET(OUT[B2], OUT[B3])
```

The meet operation depends on the particular analysis.

---

# 8. Two Major Types of Data-Flow Analysis

## Forward Analysis

Information flows:

```text
Entry → Exit
```

Examples:

* Reaching Definitions
* Available Expressions
* Constant Propagation

---

## Backward Analysis

Information flows:

```text
Exit → Entry
```

Examples:

* Live Variable Analysis
* Liveness Analysis

### 🔥 GATE Trick

```text
Reaching Definitions     → Forward
Available Expressions    → Forward
Constant Propagation     → Forward
Liveness                 → Backward
```

---

# 9. May vs Must Analysis ⭐⭐⭐⭐⭐

This is one of the most important GATE concepts.

## May Analysis

Question:

> Can this information be true along **at least one path**?

Usually uses:

```text
UNION
```

Examples:

* Reaching Definitions
* Liveness

---

## Must Analysis

Question:

> Is this information true along **all paths**?

Usually uses:

```text
INTERSECTION
```

Example:

* Available Expressions

---

| Analysis              | Direction | Meet                    | Type             |
| --------------------- | --------- | ----------------------- | ---------------- |
| Reaching Definitions  | Forward   | Union                   | May              |
| Available Expressions | Forward   | Intersection            | Must             |
| Live Variables        | Backward  | Union                   | May              |

### 🔥 Memorize

```text
RD → Forward + Union + May
AE → Forward + Intersection + Must
LV → Backward + Union + May
```

This table is extremely useful for GATE.

# 11. GEN and KILL

Many data-flow analyses use:

```text
GEN
KILL
```

### GEN

Information generated by a basic block.

### KILL

Information invalidated by a basic block.

Think:

```text
GEN  → Creates
KILL → Destroys
```

---

# 12. Generic Equation

A common form is:

```text
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

But **do not blindly apply this equation to every analysis**.

The exact equation depends on:

* analysis
* direction
* meet operator
* lattice

### ⚠️ GATE Trap

Don't memorize only:

```text
OUT = GEN ∪ (IN − KILL)
```

Memorize the complete analysis-specific equations.

---

# 13. Reaching Definitions ⭐⭐⭐⭐⭐

Question:

> Which definitions of variables may reach a program point without being killed?

Example:

```text
x = 10
y = x + 5
```

The definition:

```text
x = 10
```

reaches the second statement.

### Properties

```text
Forward
+
Union
+
May
```

Equation:

```text
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

```text
IN[B] = ⋃ OUT[P]
```

where `P` are predecessors.

---

# 14. Available Expressions ⭐⭐⭐⭐⭐

Question:

> Which expressions have definitely already been computed and are still valid?

Example:

```text
x = a + b
y = c + (a + b)
```

If `a` and `b` have not changed:

```text
a + b
```

is available.

### Properties

```text
Forward
+
Intersection
+
Must
```

Equations:

```text
IN[B] = ⋂ OUT[P]
```

```text
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

---

# 15. Live Variable Analysis ⭐⭐⭐⭐⭐

Question:

> Which variables may be used in the future?

A variable is live if its current value may be needed later.

### Properties

```text
Backward
+
Union
+
May
```

Equations:

```text
OUT[B] = ⋃ IN[S]
```

where `S` are successors.

```text
IN[B] = USE[B] ∪ (OUT[B] − DEF[B])
```

---

# 16. USE and DEF

For liveness:

### USE[B]

Variables used before being defined in the block.

### DEF[B]

Variables defined in the block.

Example:

```text
B:
    x = a + b
    y = x + c
```

Therefore:

```text
USE[B] = {a,b,c}
DEF[B] = {x,y}
```

Why isn't `x` in USE?

Because `x` is defined before it is used within the block.

---

# 17. Constant Propagation

Constant propagation determines whether a variable has a known constant value.

Example:

```text
x = 10
y = x + 5
```

Can become:

```text
x = 10
y = 15
```

It is generally treated as a:

```text
Forward data-flow analysis
```

and uses a lattice containing values such as:

```text
UNDEF
constant
NAC
```

where `NAC` means:

```text
Not A Constant
```

---

# 18. Data-Flow Lattice ⭐⭐⭐⭐

A lattice represents the possible abstract states of information.

For constant propagation:

```text
UNDEF
  ↓
constant
  ↓
NAC
```

The exact graphical orientation can differ depending on the convention used.

### Important for GATE

Understand the **meaning** of:

* `UNDEF`
* known constant
* `NAC`

rather than relying only on the drawing orientation.

---

# 19. Meet Operation Example

Suppose:

```text
Path 1 → x = 5
Path 2 → x = 5
```

At the merge:

```text
x = 5
```

can remain known.

But:

```text
Path 1 → x = 5
Path 2 → x = 10
```

gives:

```text
x = NAC
```

because there isn't one unique constant.

---

# 20. Fixed-Point Iteration ⭐⭐⭐⭐⭐

CFGs may contain loops.

Example:

```text
       B1
        ↓
       B2 ←──┐
        ↓    │
       B3 ───┘
        ↓
       Exit
```

Information can circulate around the loop.

Therefore we repeatedly apply transfer functions until the information stops changing.

This is called reaching a:

# Fixed Point

---

# 21. Fixed-Point Algorithm

General process:

```text
1. Initialize IN/OUT sets
          ↓
2. Apply transfer functions
          ↓
3. Apply meet operation
          ↓
4. Update IN/OUT
          ↓
5. Repeat
          ↓
6. No changes?
          ↓
       Fixed Point
```

### 🔥 GATE Trick

If a CFG contains a loop, **don't assume one pass is sufficient**.

---

# 22. Worklist Algorithm ⭐⭐⭐⭐

Instead of repeatedly processing every block unnecessarily, a compiler can use a **worklist algorithm**.

Basic idea:

```text
Put blocks into worklist
        ↓
Take one block
        ↓
Recalculate data-flow information
        ↓
If information changed
        ↓
Add affected neighboring blocks
```

Continue until:

```text
worklist = empty
```

This is a practical way to compute a fixed point.

---

# 23. Boundary Conditions ⭐⭐⭐⭐

The initial values depend on the analysis.

Examples:

### Reaching Definitions

At entry:

```text
IN[entry] = ∅
```

typically, assuming no relevant definitions before entry.

### Liveness

At exit:

```text
OUT[exit] = ∅
```

typically.

### Available Expressions

At entry, the set is typically initialized to:

```text
∅
```

because no expression has been computed before program entry.

⚠️ Exact initialization depends on the formulation.

---

# 24. Direction + Boundary + Meet

To correctly solve a data-flow question, identify:

```text
1. Direction
2. Meet operator
3. Boundary condition
4. Transfer function
5. Initialization
6. Fixed point
```

This is the safest GATE approach.

---

# 25. Example — Reaching Definitions

Consider:

```text
B1:
    x = 10
    goto B3

B2:
    x = 20
    goto B3

B3:
    y = x + 5
```

CFG:

```text
       B1
      /  \
     B2   ?
      \  /
       B3
```

If both definitions can reach `B3`:

```text
x = 10
x = 20
```

then:

```text
IN[B3]
```

contains both reaching definitions.

Therefore, the compiler cannot uniquely determine which definition supplied `x`.

---

# 26. Example — Available Expressions

```text
B1:
    t1 = a + b

B2:
    t2 = a + b
```

If `B2` is reached only from `B1` and neither `a` nor `b` changes:

```text
a+b
```

is available at `B2`.

Therefore `B2` can potentially reuse the earlier result.

---

# 27. Example — Liveness

```text
B1:
    x = a + b
    y = x + c
```

At the end of the block:

If `y` is required later:

```text
y → LIVE
```

But after its final use:

```text
x → DEAD
```

and its register can potentially be reused.

# 30. May vs Must — Easy Example ⭐⭐⭐⭐⭐

Suppose:

```text
B1 computes X
B2 computes X
```

and both flow into:

```text
B3
```

### Question:

Is `X` available at `B3`?

It must have been computed on **both paths**.

Therefore:

```text
X ∈ OUT[B1] ∩ OUT[B2]
```

Hence:

```text
Available Expressions → Intersection
```

---

Now suppose:

```text
B1 defines x
B2 defines y
```

At `B3`, we ask:

> Which definitions may reach?

Any definition from either path may reach.

Therefore:

```text
Union
```

# 32. IN and OUT Equations — Memorize

## Reaching Definitions

```text
IN[B] = ⋃ OUT[P]
```

```text
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

---

## Available Expressions

```text
IN[B] = ⋂ OUT[P]
```

```text
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

---

## Liveness

```text
OUT[B] = ⋃ IN[S]
```

```text
IN[B] = USE[B] ∪ (OUT[B] − DEF[B])
```

---

# 33. 🔥 One Formula Pattern to Remember

For the first two:

```text
OUT = GEN ∪ (IN − KILL)
```

But the difference is:

```text
RD:
IN = UNION predecessor OUT

AE:
IN = INTERSECTION predecessor OUT
```

For liveness, direction reverses:

```text
LV:
OUT = UNION successor IN
IN = USE ∪ (OUT − DEF)
```

# 34. Common GATE Traps ⚠️

### Trap 1

> All data-flow analyses are forward.

❌ False.

Liveness is backward.

---

### Trap 2

> All data-flow analyses use union.

❌ False.

Available expressions uses intersection.

---

### Trap 3

> May analysis uses intersection.

❌ Usually false in these standard bit-vector analyses.

May → typically union.

---

### Trap 4

> Must analysis uses union.

❌ Typically false.

Must → intersection.

---

### Trap 5

> `GEN` means all information appearing in a block.

❌ No.

It represents information generated in a way that is relevant at the block's output.

---

### Trap 6

> `KILL` means the variable is deleted.

❌ No.

It means previously available information is invalidated.

---

### Trap 7

> One iteration always gives the final answer.

❌ False for CFGs with loops.

---

### Trap 8

> IN always comes from predecessors.

❌ False.

For backward analysis, information is derived from **successors**.

# 38. PYQ Pattern 4 — Compute IN/OUT

Given:

```text
USE[B] = {a,b}
DEF[B] = {c}
OUT[B] = {a,c,d}
```

Calculate:

```text
IN[B]
= USE ∪ (OUT − DEF)
```

Therefore:

```text
OUT − DEF
= {a,d}
```

and:

```text
IN
= {a,b,d}
```

---

# 39. PYQ Pattern 5 — Loop

Given a CFG with:

```text
B1 → B2
B2 → B3
B3 → B2
```

Don't calculate only once.

Use:

```text
Fixed-point iteration
```

until:

```text
IN/OUT values stop changing.
```

---

# 40. PYQ Pattern 6 — Maximum Register Requirement

If the question provides liveness information:

```text
Point 1 → {a,b}
Point 2 → {a,b,c}
Point 3 → {b,c}
```

Maximum simultaneous live values:

```text
3
```

Therefore at least 3 registers may be needed for those values, subject to the machine/register-allocation assumptions.

---

# 41. PYQ Pattern 7 — CSE

If asked:

> Can `a+b` be reused?

Check:

```text
Was a+b already computed?
        ↓
Are a and b unchanged?
        ↓
Is the previous result still valid?
```

If yes:

```text
CSE possible
```

# 42. PYQ Pattern 8 — Constant Propagation

```text
x = 5
...
y = x + 10
```

If no intervening definition changes `x`:

```text
x = 5
```

can be propagated.

# 43. Bit-Vector Framework ⭐⭐⭐⭐

Many classical data-flow problems can be represented using **bit vectors**.

Each bit represents whether some fact is true.

For example, in reaching definitions:

```text
D1 D2 D3 D4
```

A set such as:

```text
{D1,D3}
```

can be represented as:

```text
1010
```

depending on bit ordering.

---

# 44. Why Bit Vectors?

Bit-vector representation makes data-flow operations efficient.

For example:

### Union

Can be implemented using:

```text
OR
```

### Intersection

Can be implemented using:

```text
AND
```

### Difference

Can be implemented using:

```text
AND + complement
```

Conceptually:

```text
A − B = A AND NOT(B)
```

### 🔥 GATE Trick

If GATE gives bit vectors, think:

```text
Union        → OR
Intersection → AND
Difference   → AND with complement
```

# 45. Monotonicity and Fixed Points

A transfer function should behave consistently with the information ordering used by the analysis.

Repeated application should converge under the usual finite-domain framework.

For GATE, the key practical idea is:

```text
Finite data-flow domain
+
Monotonic transfer functions
        ↓
Fixed-point iteration
        ↓
Convergence
```

---

# 46. Worklist vs Naive Iteration

### Naive approach

Process:

```text
B1,B2,B3,...,Bn
```

again and again.

### Worklist approach

Only revisit blocks whose inputs may have changed.

This can be much more efficient.

For GATE, understand the concept rather than memorizing implementation details.


