# Type Erasure

## What is Type Erasure?

**Type Erasure** is the process by which the Java compiler removes generic type information during compilation.

Generics exist only at **compile time** to provide type safety. After compilation, the generated bytecode contains normal Java classes without generic type information.

> **Definition:** Type Erasure is the compiler process that removes generic type parameters and replaces them with their upper bound (or `Object` if no bound exists).

---

# Why Do We Need Type Erasure?

Java Generics were introduced in **Java 5**.

Before Java 5,

```java
ArrayList list = new ArrayList();
```

After Java 5,

```java
ArrayList<String> list = new ArrayList<>();
```

Older Java applications still needed to work.

Type Erasure allows new generic code to remain compatible with old non-generic bytecode.

---

# Real-World Example

Imagine a package.

During packing

```text

Compiler Knows

↓

Contains String
```

After shipping

```text
Box

↓

Generic Label Removed
```

The label disappears,

but the contents remain valid.

Similarly,

Generics disappear after compilation.

```text

↓

↓

↓

↓

JVM Execution
```

Generics help during compilation,

not during runtime.

Source Code


After Type Erasure

```java
List list = new ArrayList();

list.add("Java");
```

Notice

```text
<String>

↓

Removed
```

# Example 2

```java
class Box<T>{

    private T value;

}
```

After Type Erasure

```java
class Box{

    private Object value;

}
```

Because

```java
T
```

has no bound,

it becomes

```java
Object
```

---

# Upper Bound Example

```java
class Box<T extends Number>{

    T value;

}
```

After Type Erasure

```java
class Box{

    Number value;

}
```

Since

```java
T extends Number
```

the compiler replaces `T` with `Number`.

---

# Generic Method Example

Before

```java
public <T> void print(T value){

    System.out.println(value);

}
```

After Type Erasure

```java
public void print(Object value){

    System.out.println(value);

}
```

# Compile-Time Type Safety

Suppose

```java
List<String> list = new ArrayList<>();

list.add("Java");

// list.add(100);
```

Compiler

```text
Error

↓

Expected String

↓

Found Integer
```

The compiler prevents invalid code.

At runtime,

there are no generic checks.

---

# Why Casting Still Works

Example

```java
List<String> list = new ArrayList<>();

String name = list.get(0);
```

After Type Erasure

```java
List list = new ArrayList();

String name = (String) list.get(0);
```

The compiler automatically inserts the required cast.

---

# Runtime Example

```java
List<String> list1 = new ArrayList<>();

List<Integer> list2 = new ArrayList<>();
```

Runtime

```text
list1

↓

ArrayList

----------------

list2

↓

ArrayList
```

Both become the same runtime class.

---

# Proof

```java
List<String> list1 = new ArrayList<>();

List<Integer> list2 = new ArrayList<>();

System.out.println(
    list1.getClass() == list2.getClass()
);
```

Output

```text
true
```

Because both are simply

```text
ArrayList
```

after Type Erasure.

---

# Cannot Create Generic Arrays

Invalid

```java
T[] arr = new T[10];
```

Reason

The actual type of `T` is unknown at runtime.

---

# Cannot Create Generic Objects

Invalid

```java
new T();
```

Reason

The JVM doesn't know what `T` is after Type Erasure.

---

# Cannot Use instanceof

Invalid

```java
if(obj instanceof List<String>)
```

Correct

```java
if(obj instanceof List)
```

Generic information isn't available at runtime.

---

# Bridge Methods

Sometimes,

Type Erasure changes method signatures.

The compiler creates **Bridge Methods** to preserve polymorphism.

Example

```java
class Parent<T>{

    T get(){

        return null;

    }

}
```

```java
class Child extends Parent<String>{

    @Override
    String get(){

        return "Java";

    }

}
```

The compiler generates a hidden bridge method so that overriding continues to work correctly after Type Erasure.

You normally don't write bridge methods yourself.

# Production Usage

Type Erasure is used automatically in every Java application.

Examples

- Collections Framework
- Spring Boot
- Hibernate
- Streams API
- Optional
- CompletableFuture

Developers usually don't interact with Type Erasure directly, but understanding it explains many Generic limitations.

---

# Advantages

- Backward compatibility
- Compile-time type safety
- No runtime overhead for Generics
- Existing JVM architecture remains unchanged

---

# Limitations

- Generic type information is unavailable at runtime
- Cannot create `new T()`
- Cannot create generic arrays
- Cannot use `instanceof` with parameterized types
- Reflection has limited generic information

---

# Best Practices

✅ Use Generics for compile-time safety.

✅ Don't rely on Generic type information at runtime.

✅ Prefer collections over generic arrays.

✅ Understand Type Erasure before using reflection with Generics.

---

# Interview Questions

### 1. What is Type Erasure?

The compiler process that removes Generic type information during compilation.

---

### 2. Why does Java use Type Erasure?

To provide backward compatibility with code written before Generics were introduced.

---

### 3. What replaces an unbounded type parameter?

`Object`

---

### 4. What replaces a bounded type parameter?

Its upper bound.

Example

```java
<T extends Number>
```

becomes

```java
Number
```

---

### 5. Do Generics exist at runtime?

No.

Most Generic type information is removed during compilation.

---

### 6. Why can't we create `new T()`?

Because the actual type of `T` is unknown after Type Erasure.

---

### 7. Why can't we create Generic arrays?

Because the runtime doesn't know the actual Generic type.

---

### 8. Why does `list1.getClass() == list2.getClass()` return `true`?

Because both `List<String>` and `List<Integer>` become `ArrayList` after Type Erasure.

---

### 9. What are Bridge Methods?

Compiler-generated methods that preserve method overriding after Type Erasure.

---

### 10. Does Type Erasure reduce performance?

No.

It enables compile-time type checking without adding significant runtime overhead.

---

# Quick Revision

- Type Erasure removes Generic type information.
- Happens during compilation.
- Unbounded `T` → `Object`
- Bounded `T` → Upper Bound
- Generics exist mainly at compile time.
- Cannot:
  - `new T()`
  - `new T[]`
  - `instanceof List<String>`
- Bridge Methods preserve polymorphism.
- Ensures backward compatibility.
